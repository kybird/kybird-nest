# kybird-nest — 설계 SSOT

> 작성: 2026-08-08
> 원재료: [seed-2026-08-08.md](seed-2026-08-08.md)
>
> 이 문서가 SSOT다. seed 문서는 출발점 기록이며, 거기 남아있던 "재검토 필요"
> 항목은 이 문서에서 대부분 해소됐다. 충돌하면 이 문서가 이긴다.

## 한 줄 정의

코딩 에이전트를 위한 **지식·스킬 백엔드**와, 그 위에 얹은 칸반/대시보드.
서버는 저장과 동기화만 하고, 계산은 전부 클라이언트가 한다.

## 1. 확정된 요구사항

### 1.1 계정 · 레포

> **2026-08-09 갱신**: 아래 두 줄은 원래 "레포는 계정 단독 소유, 유저 간
> 공유 없다"였다. 실사용 시작 시점에 방향이 뒤집혔다 — 여러 사람이 같은
> 프로젝트에서 지식을 공유하는 유즈케이스가 "한 사람이 여러 기기에서
> 쓰는" 유즈케이스를 포함하는 상위 집합이라는 판단. `RepoMember`/
> `RepoInvite`로 구현했다(레포별 참여 코드, 멤버는 역할 구분 없이 동일
> 권한). git clone만으로 자동 합류는 안 된다 — 참여 코드가 있어야 한다.

- 계정 관리 필요. **1인 이상** 사용 가능해야 한다(멀티유저).
- 레포(프로젝트)는 **멤버십에 종속**된다 — 만든 사람이 아니라 참여 코드로
  합류한 멤버 전원이 동일하게 접근한다(읽기/쓰기, 역할 구분 없음).
- 레포가 **git 프로젝트가 아닐 수도 있다.** git 연동은 선택이지 전제가 아니다.
- 인증은 단순하게: 로그인 → 토큰 발급 → 클라이언트가 `~/.kybird/config`에 보관.
  **레포 안에 두지 않는다**(커밋 사고 방지).

### 1.2 스킬

- 백엔드가 스킬들을 보유한다. 레포별로 **활성/비활성** 지정.
- 클라이언트가 스킬을 수정할 수 있다.
  → **원본(부모)은 고정 보존**, 수정본은 **상속받은 파생 스킬로 별도 보관.**
- 부모 스킬이 갱신되면 **LLM이 매개해서 파생본을 리베이스**한다.
  사람이 최종 승인. 이전 파생본은 지우지 않는다(= 버전 히스토리).
- **개인화 메모(2026-08-09)**: "레포는 공유, 개인 커스터마이징은 별도"
  요구가 나왔을 때, 카드/wiki 단위 개인 스코프는 안 만들기로 했다(1.1
  갱신 참고) — 그 대신 이 스킬 파생본의 "개인 오버라이드"는 Claude
  Code의 네이티브 패턴을 그대로 재사용하는 방향이 유력하다: 공유
  `CLAUDE.md`(git 커밋) + 개인 `CLAUDE.local.md`(gitignore, 같이
  로드돼서 이어붙여짐). kybird-nest 쪽엔 DB 스키마가 필요 없고,
  클라이언트가 이 두 파일을 생성/갱신하는 역할만 하면 된다. 아직
  미구현 — 이 단계 실제 작업 시 확정할 것.

### 1.3 wiki

- 클라이언트가 프로젝트 지식을 백엔드에 **주입**하고 **검색**한다.
- 기본 개념은 Andrej Karpathy의 llm-wiki를 따른다.
- **semantic 검색** 지원, **index.md** 지원.
- 초안은 현재 TTSTextViewer의 `wiki-*` 스킬을 재사용한다.
- **cross-project 검색은 "한 유저가 멤버인 레포들 사이"에서** 성립한다
  (1.1 갱신 참고 — 이제 "가진"이 아니라 "멤버인"이다). 레포 안에서는
  멤버 전원이 같은 wiki를 본다 — 유저 간 공유가 **없는 게 아니라 레포
  멤버십이 곧 공유 범위다.**

### 1.4 칸반

- 칸반과 wiki를 유기적으로 통합한다. 연결 방향은 **카드 ↔ wiki 양방향.**
- **에이전트도 칸반을 조작한다**(카드 생성·이동·상태 변경).
- 프론트엔드에서 현재 상황을 **한눈에** 볼 수 있어야 한다.

### 1.5 동기화 · 오프라인

- **서버가 진실**이다. 클라이언트는 서버와 동기화한다.
- **서버는 저장소에 가깝다.** 동기화가 주목적이다.
- **오프라인 동작은 필수.** 서버가 없어도 작업이 막히지 않는다.
- **임베딩·검색·컴파일은 전부 클라이언트**에서 한다. 서버는 벡터를 blob으로만 취급.

### 1.6 평가

- wiki 시스템은 실험 단계다. **성능 지표를 시스템에 내재**시켜서, 개선이
  실제 개선인지 판단할 수 있어야 한다.
- 비교 대상 = **스킬의 부모/파생 체인**. 즉 스킬 상속이 곧 버전 관리다.

## 2. 지식 주입 — 3층 구조

에이전트가 말을 듣게 **강제할 방법은 없다.** 대신 비협조를
**데이터 손실이 아니라 지연으로 강등**시킨다.

| 층 | 트리거 | 에이전트 협조 | 품질 |
|---|---|---|---|
| 명시적 호출 | 에이전트가 `wiki-log` 호출 | 필요 | 높음 |
| git hook | commit / push | 불필요 | 중간 |
| backfill | 사람이 아무 때나 실행 | 불필요 | 낮음~중간 |

- 위층이 비면 아래층이 받는다. **어느 층도 없어서 지식이 영영 사라지는 구간이 없다.**
- **git hook은 큐에 넣고 즉시 종료한다.** 훅에서 LLM을 부르면 커밋이 느려지고,
  그러면 `--no-verify`로 꺼버리게 된다. 실제 처리는 비동기로.
- git이 아닌 레포도 있으므로 **명시적 호출이 정본, hook은 편의 기능**이다.
- backfill = 커밋 diff/메시지를 LLM에 먹여 뒤늦게 엔트리를 생성.

### pull 쪽 지렛대

에이전트는 `wiki-search`를 **자발적으로** 쓴다(자기한테 이득이므로).
그러므로 **검색 응답에 "작업 끝나면 wiki-log 남겨라" 리마인더를 실어 보낸다.**
AGENTS.md는 세션 시작에 한 번 읽히고 잊히지만, 이건 에이전트가 관심을 갖는
바로 그 순간에 눈앞에 놓인다.

부수 효과로, **평가용 검색 로그가 협조 없이 저절로 쌓인다.**

## 3. 아키텍처

### 3.1 무게 분포

서버를 일부러 바보로 만들었기 때문에 무게가 클라이언트로 갔다. 의도된 트레이드다.
서버가 똑똑하면 오프라인이 깨지고, 서버가 멍청하면 클라가 무거워지는데
후자가 훨씬 다루기 쉽다.

**서버** — 인증, 저장, 동기화 API. 끝. 임베딩·검색·컴파일 안 한다.

**클라이언트** — 로컬 스토어, 오프라인 큐, 싱크 엔진, 임베딩, 검색,
index.md 컴파일, 스킬 파일 생성, 드리프트 감지, LLM 리베이스, git hook,
backfill, MCP 서버, 칸반 조작.

### 3.2 클라이언트 구조 — 코어 + 얇은 표면

CLI 하나로 만들면 MCP 붙일 때 절반을 다시 짜게 된다. 반드시 분리한다.

```
core (라이브러리)
  store    — 로컬 SQLite
  sync     — 서버 push/pull, 오프라인 큐
  wiki     — 주입, 임베딩, 검색, 컴파일
  skills   — 구현체 생성, 드리프트 감지, 상속/리베이스
  kanban   — 카드 조작
        ↑ 아래 표면들은 core를 부르기만 한다
표면
  nest CLI     — 사람이 치는 것
  nest mcp     — 에이전트가 붙는 것 (같은 프로세스, 서브커맨드)
  git hook     — 큐에 넣고 즉시 종료
```

**에이전트별 훅을 N개 지원하지 않는다. MCP 하나로 간다.**
Claude Code · Cursor · Windsurf · Copilot 모두 MCP를 지원하므로 이게
실질적인 이식성 답이다. MCP도 에이전트가 "호출하기로 선택"해야 하는 건
같지만, 훅 파편화 문제는 사라진다.

## 4. 기술 결정

### 언어 — 전부 TypeScript
서버가 Next.js고 MCP SDK가 TS 네이티브다. 무엇보다 싱크 프로토콜은
서버/클라가 타입을 공유하면 버그가 크게 줄어드는 종류의 코드다.
Python이 임베딩 생태계는 낫지만 언어 두 개를 유지할 값어치는 없다.

### 스택 — Next.js + Prisma + SQLite
로컬 스토어도 SQLite(`better-sqlite3`). 서버와 스키마 모양을 맞추면
싱크가 "행 단위 대조"로 단순해진다.

### 마크다운은 진실이 아니라 export
사람이 읽고 Obsidian으로 열려고 뽑는 뷰다.
**마크다운을 싱크 단위로 삼으면 seed 문서에 기록된 그 지옥이 재현된다.**

### 임베딩 — 로컬 모델, 교체 가능
오프라인 우선이므로 API 임베딩은 주입을 막는다. 코퍼스도 500개 수준이라
작은 로컬 모델로 충분하다. **벡터마다 생성에 쓴 모델·차원을 함께 저장**해서
나중에 모델을 바꿔도 비교가 가능하게 한다.

### 검색 — 키워드 + 벡터 하이브리드
어느 하나보다 낫다. 그리고 **검색 전략을 갈아끼울 수 있는 구조 자체가
평가 시스템의 전제**다. "이번 버전이 나아졌나"를 재려면 전략을 바꿔가며
같은 질문셋을 돌릴 수 있어야 한다.

### 동기화 — 단일 유저라 쉬운 케이스
- 레코드 id는 **클라이언트가 생성**(cuid). 오프라인에서 서버 왕복이 필요 없다.
- 서버는 단조증가 `seq`만 찍는다.
- pull = "내 커서보다 큰 seq 다 줘", push = dirty 행 전송.
- 충돌은 **최후 승자 승리 + 진 쪽을 사본으로 보존.**
- **CRDT 만들지 않는다.** 혼자 쓰는데 필요 없다.

### 칸반 순서 — 문자열 분수 랭크
`order Int`는 **틀렸다.** 오프라인에서 두 머신이 카드를 옮기면 정수 순서는
반드시 충돌한다. lexo-rank류 문자열 랭크를 쓴다.

### 파생 스킬 저장 — 전문 + 부모 버전 포인터
patch를 저장하지 않는다. 전문을 들고 있으면 바로 쓸 수 있고,
diff는 필요할 때 `부모@그버전 vs 내것`으로 계산하면 된다.
patch 저장은 재구성이 깨지기 쉽다.

**리베이스 흐름**: 부모 v1→v2 감지 → `diff(부모v1, 내것)`과
`diff(부모v1, 부모v2)`를 LLM에 전달 → 병합본 수령 → 사람이 승인 →
파생 v2 생성(`parentVersion=2`). 이전 파생본은 남긴다.

### 스킬 편집 UX — 별도 명령 없음
`.claude/skills/` 안의 파일을 평소처럼 고친다. `nest sync`가 드리프트를
감지하면 "원본과 달라졌는데 파생 스킬로 만들까?"라고 묻는다.
새 워크플로를 배울 필요가 없고, 실수로 날릴 일도 없다.

### 검색 로그는 첫날부터
매 검색마다 `(질문, 반환 결과, 사용된 스킬 버전, 에이전트가 실제로 쓴 결과)`를
기록한다. **나중에 소급이 불가능한 유일한 것**이다. 이 로그에 사후 라벨링만
하면 평가용 정답셋이 공짜로 생긴다.

## 5. 평가 지표 — 나중에, 로깅은 지금

표준 지표는 대략 이렇다:
- 검색이 정답 문서를 상위 k개에 넣었는가 — **recall@k**
- 몇 번째에 넣었는가 — **MRR / nDCG**
- 답변 품질 — 보통 **LLM-as-judge**

셋 다 **"이 질문엔 이 문서가 나와야 한다"는 정답셋이 있어야** 잴 수 있다.
지금 만들 필요 없다. **로깅만 처음부터 하면 정답셋은 나중에 싸게 만들어진다.**

## 6. 만드는 순서

가장 안 해본 것(싱크, 검색 품질)을 먼저 깨고, 아는 것(CRUD, UI)을 뒤로 민다.

1. **서버 + 싱크 + 칸반** — 칸반을 싱크 프로토콜의 실험동물로 쓴다.
   제일 단순한 엔티티라 프로토콜 버그가 그대로 드러나고, 끝나면 눈에 보이는
   물건이 하나 나온다.
2. **wiki** — 명시적 주입, 로컬 인덱스, 하이브리드 검색, index.md 컴파일.
   **검색 로그는 여기서부터 무조건.**
3. **MCP + git hook + backfill** — 에이전트가 실제로 쓰기 시작하는 지점.
   3층 주입 완성.
4. **스킬** — 싱크, 구현체 생성, 드리프트→파생, LLM 리베이스.
5. **대시보드 + 카드↔wiki 연결** — "카드 작업 중 나온 지식이 그 카드에 붙는다"가
   통합의 실체이자 한눈에 보기의 알맹이.
6. **평가 하네스** — 2단계부터 쌓인 로그에 라벨을 붙여 정답셋을 만들고
   스킬 버전 간 비교.

> **1~3이 실제 제품이고 4~6은 확장이다.** 3단계까지 가면 혼자 쓰기엔 충분히
> 돌아간다. 거기서 실제로 써본 뒤 4~6의 우선순위를 다시 정한다.
> 지금 6단계까지 확정 설계하면 4~6은 거의 확실히 틀리게 그려진다.

## 7. 미결 / 보류

1. **CLI 이름** — `nest`가 유력하나 미확정(seed 문서에서도 미확정).
2. **지식의 프로젝트 독립성** — 주입 시점에 아예 "프로젝트 종속 / 프로젝트 독립"을
   구분해 저장하는 안이 나왔으나 미결. cross-project 검색의 품질과 직결된다.
3. **세션 저장** — 서버에 저장하는 건 스코프 밖으로 판단. 다만 로컬에 이미 있는
   에이전트 트랜스크립트를 **사후에 긁어오는** 형태는 열려 있다.
   에이전트별로 위치·포맷이 다르지만 **읽기 전용이라 하나씩 늘리면 되고,
   미지원 도구는 backfill로 떨어지므로 깨지지 않는다.**
   **2026-08-09 메모**: 이게 필요한 이유는 git 커밋이 "최종 결과"만 남기기
   때문이다 — 시행착오·버린 시도·커밋 없이 끝난 세션(조사만 하고 끝, 설정
   삽질)은 커밋 기반 backfill에 아예 안 잡힌다. 다만 이건 커밋 기반
   backfill과 별개로 **진짜 파편화 문제**다 — 세션 트랜스크립트는 git에
   안 들어가는 로컬 파일이라 각자 자기 머신에만 있다. (레포 공유 기능을
   만들면서 다른 파편화 문제 하나는 이미 고쳤다: `ingest_queue`가 로컬
   전용이라 팀원끼리 "이 커밋 이미 처리했나"를 몰랐던 것 — `WikiEntry.
   sourceRef`로 이미 처리된 커밋인지 확인하는 걸로 해결, `Store.
   hasSourceRef()`. 이건 커밋 자체가 git으로 이미 공유되니까 가능했던
   것이고, 세션 트랜스크립트는 애초에 공유되는 원본이 없어서 같은 수로는
   못 푼다.)
