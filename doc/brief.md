## 한 줄 정의

코딩 에이전트를 위한 **지식·스킬 백엔드**와, 그 위에 얹은 칸반/대시보드.
서버는 저장과 동기화만 하고, 계산은 전부 클라이언트가 한다.

그건 **무엇**이고, **왜**는 0장에 있다.

## 0. 왜 만드는가 — 세 개의 루프 (2026-08-11 추가)

최종 목표는 지식 백엔드 자체가 아니다. **에이전트 루프 세 개가 칸반을
매개로 서로 물고 도는 자동화 파이프라인**이고, 지식·칸반은 그 루프들이
상태를 주고받는 배관이다.

| 루프 | 사람 세상의 대응물 | 입력 | 출력 |
|---|---|---|---|
| 기획 | 기획회의, 요구사항 정리, 제품설계 | 의도·기각된 카드 | 할 일 카드 |
| 개발 | 실제 작업자 | 할 일 카드 | 완료 카드 |
| QA | 검증 | 완료 카드 | 통과 / 기각 |

**기각은 상류로 되돌아간다.** QA가 기각하면 개발 루프의 할 일로, 개발이
기각하면(요구사항이 틀렸거나 불가능) 기획 루프의 할 일로. 각 루프의
출력이 하류의 입력이고, 기각 경로가 순환을 닫는다.

### 왜 칸반이 매개인가

루프들은 **같은 세션에 있지 않다** — 다른 시각, 다른 모델, 다른 머신일
수 있다. 공유 메모리가 없으므로 상태는 반드시 프로세스 밖에 있어야 하고,
서버에 있는 칸반이 그 자리다.

그래서 기존 결정 두 개가 편의가 아니라 **전제**가 된다: "에이전트도 칸반을
조작한다"(1.4), "서버가 진실"(1.5). 회귀 추적(`↺N`, `completedAt`/
`regressCount`)도 장식이 아니라 **루프가 헛도는지 재는 계기판**이다 —
같은 카드가 QA에서 반복해 튕겨나오면 그 루프는 수렴하지 않는 것이고,
사람이 개입해야 한다는 신호다.

### 왜 무인이어야 하는가 — 오프피크 레버리지

주 워커로 쓰는 Z.AI는 **시간대별 요금이 다르다.** 사람이 자는 시간에
돌리면 같은 작업이 싸다. 이걸 실제로 쓰려면 루프가 사람 개입 없이 몇 시간
연속으로 돌아야 한다. 이 제약이 설계에 직접 내려온다:

- **사람 승인을 루프 안에 두지 않는다.** 승인 대기 = 오프피크 낭비다.
  승인은 루프 밖으로 뺀다(아침에 사람이 몰아서).
- **실패해도 멈추지 않는다.** 카드 하나가 막히면 다음 카드로 가고, 막힌
  건 회귀로 남긴다. 한 카드가 밤을 통째로 잡아먹으면 안 된다.
- **서버가 죽어도 로컬 작업은 계속된다**(1.5 오프라인 우선). 밤새 서버
  장애로 몇 시간을 날리지 않기 위해서다.

### 지금 어디까지 왔나

**개발 루프만 돌아간다.** 기획·QA 루프는 없고, 오프피크 기동 스케줄링도
없다. 이 문서의 1~7장은 사실상 **전부 개발 루프의 배관**이라고 읽으면
된다. 나머지 두 루프는 이 배관 위에 얹힐 것이고, 얹히면서 요구사항이
바뀔 수 있다.

그리고 이건 제품이 아니라 **실험이다.** 효율적인 자동화 루프가 실제로
성립하는지 보고 고치는 게 목적이므로, 위 구조 자체도 확정이 아니다.

## 1. 확정된 요구사항

### 1.1 계정 · 레포

> **2026-08-09 갱신**: 아래 두 줄은 원래 "레포는 계정 단독 소유, 유저 간
> 공유 없다"였다. 실사용 시작 시점에 방향이 뒤집혔다 — 여러 사람이 같은
> 프로젝트에서 지식을 공유하는 유즈케이스가 "한 사람이 여러 기기에서
> 쓰는" 유즈케이스를 포함하는 상위 집합이라는 판단. `RepoMember`/
> `RepoInvite`로 구현했다(레포별 참여 코드, 멤버는 역할 구분 없이 동일
> 권한). git clone만으로 자동 합류는 안 된다 — 참여 코드가 있어야 한다.

- 계정 관리 필요. **1인 이상** 사용 가능해야 한다(멀티유저).
- 레포(프로젝트)는 **멤버십에 종속**된다 — 만든 사람이 아니라 참여 코드로
  합류한 멤버 전원이 동일하게 접근한다(읽기/쓰기, 역할 구분 없음).
- 레포가 **git 프로젝트가 아닐 수도 있다.** git 연동은 선택이지 전제가 아니다.
- 인증은 단순하게: 로그인 → 토큰 발급 → 클라이언트가 `~/.kybird/config`에 보관.
  **레포 안에 두지 않는다**(커밋 사고 방지).

### 1.2 스킬

- 백엔드가 스킬들을 보유한다. 레포별로 **활성/비활성** 지정.
- 클라이언트가 스킬을 수정할 수 있다.
  → **원본(부모)은 고정 보존**, 수정본은 **상속받은 파생 스킬로 별도 보관.**
- 부모 스킬이 갱신되면 **LLM이 매개해서 파생본을 리베이스**한다.
  사람이 최종 승인. 이전 파생본은 지우지 않는다(= 버전 히스토리).
- **개인화 메모(2026-08-09)**: "레포는 공유, 개인 커스터마이징은 별도"
  요구가 나왔을 때, 카드/wiki 단위 개인 스코프는 안 만들기로 했다(1.1
  갱신 참고) — 그 대신 이 스킬 파생본의 "개인 오버라이드"는 Claude
  Code의 네이티브 패턴을 그대로 재사용하는 방향이 유력하다: 공유
  `CLAUDE.md`(git 커밋) + 개인 `CLAUDE.local.md`(gitignore, 같이
  로드돼서 이어붙여짐). kybird-nest 쪽엔 DB 스키마가 필요 없고,
  클라이언트가 이 두 파일을 생성/갱신하는 역할만 하면 된다. 아직
  미구현 — 이 단계 실제 작업 시 확정할 것.
- **부트스트랩 스킬 (2026-08-10, 구현함)**: 위 부모/파생 상속 체계와는
  별개로, 훨씬 작은 걸 먼저 만들었다 — `knest link`/`repo join` 시점에
  `.claude/skills/knest/SKILL.md`를 자동 생성한다(`packages/core/src/
  skills.ts`). CLI를 주 표면으로 앞세우면서 "에이전트가 이 도구의 존재를
  어떻게 아는가"가 빈자리가 됐는데(MCP는 툴 목록에 자동으로 뜨지만 CLI는
  AGENTS.md를 읽어야만 안다), 그 빈자리를 매번 손으로 안 써도 되게 메운
  것뿐이다. 마커 주석으로 사용자가 직접 고친 파일은 안 덮어쓴다(git hook
  설치가 남의 훅을 안 건드리는 것과 같은 패턴). 서버에 스킬을 저장하지
  않는다 — 지금은 정적 템플릿 하나를 로컬에 쓰는 게 전부다.

### 1.3 wiki

- 클라이언트가 프로젝트 지식을 백엔드에 **주입**하고 **검색**한다.
- 기본 개념은 Andrej Karpathy의 llm-wiki를 따른다.
- **semantic 검색** 지원, **index.md** 지원.
- 초안은 현재 TTSTextViewer의 `wiki-*` 스킬을 재사용한다.
- **cross-project 검색은 "한 유저가 멤버인 레포들 사이"에서** 성립한다
  (1.1 갱신 참고 — 이제 "가진"이 아니라 "멤버인"이다). 레포 안에서는
  멤버 전원이 같은 wiki를 본다 — 유저 간 공유가 **없는 게 아니라 레포
  멤버십이 곧 공유 범위다.**

### 1.4 칸반

- 칸반과 wiki를 유기적으로 통합한다. 연결 방향은 **카드 ↔ wiki 양방향.**
- **에이전트도 칸반을 조작한다**(카드 생성·이동·상태 변경).
- 프론트엔드에서 현재 상황을 **한눈에** 볼 수 있어야 한다.

> 0장 참고: 칸반은 보조 기능이 아니라 **세 루프가 상태를 주고받는 유일한
> 매개**다. 그래서 "에이전트도 조작한다"가 있으면 좋은 기능이 아니라 전제다.

### 1.5 동기화 · 오프라인

- **서버가 진실**이다. 클라이언트는 서버와 동기화한다.
- **서버는 저장소에 가깝다.** 동기화가 주목적이다.
- **오프라인 동작은 필수.** 서버가 없어도 작업이 막히지 않는다.
- **임베딩·검색·컴파일은 전부 클라이언트**에서 한다. 서버는 벡터를 blob으로만 취급.

### 1.6 평가

- wiki 시스템은 실험 단계다. **성능 지표를 시스템에 내재**시켜서, 개선이
  실제 개선인지 판단할 수 있어야 한다.
- 비교 대상 = **스킬의 부모/파생 체인**. 즉 스킬 상속이 곧 버전 관리다.

## 2. 지식 주입 — 3층 구조

에이전트가 말을 듣게 **강제할 방법은 없다.** 대신 비협조를
**데이터 손실이 아니라 지연으로 강등**시킨다.

| 층 | 트리거 | 에이전트 협조 | 품질 |
|---|---|---|---|
| 명시적 호출 | 에이전트가 `wiki-log` 호출 | 필요 | 높음 |
| git hook | commit / push | 불필요 | 중간 |
| backfill | 사람이 아무 때나 실행 | 불필요 | 낮음~중간 |

- 위층이 비면 아래층이 받는다. **어느 층도 없어서 지식이 영영 사라지는 구간이 없다.**
- **git hook은 큐에 넣고 즉시 종료한다.** 훅에서 LLM을 부르면 커밋이 느려지고,
  그러면 `--no-verify`로 꺼버리게 된다. 실제 처리는 비동기로.
- git이 아닌 레포도 있으므로 **명시적 호출이 정본, hook은 편의 기능**이다.
- backfill = 커밋 diff/메시지를 LLM에 먹여 뒤늦게 엔트리를 생성.

### pull 쪽 지렛대

에이전트는 `wiki-search`를 **자발적으로** 쓴다(자기한테 이득이므로).
그러므로 **검색 응답에 "작업 끝나면 wiki-log 남겨라" 리마인더를 실어 보낸다.**
AGENTS.md는 세션 시작에 한 번 읽히고 잊히지만, 이건 에이전트가 관심을 갖는
바로 그 순간에 눈앞에 놓인다.

부수 효과로, **평가용 검색 로그가 협조 없이 저절로 쌓인다.**

### post-commit 안내 — 유일하게 보장된 접점 (2026-08-10 추가)

위의 pull 지렛대에는 구멍이 있다. **에이전트가 검색을 안 하면 리마인더도
영영 안 뜬다.** MCP 툴이든 CLI든 AGENTS.md든 마찬가지고, 그러면 커밋은
큐에 쌓이기만 하고 아무도 그 사실을 모른 채 썩는다. "지연으로 강등"이
영원히 안 끝나면 실질적으로 손실과 구분이 안 된다.

**커밋은 반드시 한다.** 그리고 훅이 출력한 건 git 이 자기 stderr 로
흘려보내서 `git commit` 을 실행한 쪽(사람이든 에이전트 컨텍스트든)에
반드시 들어간다. 그래서 post-commit 훅이 큐에 넣은 직후, 방금 한 작업을
기록하라는 안내 한 줄을 출력한다 — 선택의 여지가 없는 유일한 자리다.
게다가 이 순간이 기록 품질도 가장 좋다. 방금 한 작업의 맥락이 아직
살아있어서, 나중에 diff 만 보고 복원하는 backfill 보다 늘 낫다.

**LLM 은 여전히 안 부른다** — 로컬 카운트 한 번이라 커밋이 안 느려진다.
위의 "훅에서 LLM 부르면 --no-verify 로 꺼버린다"는 판단은 그대로 유효하다.

하네스 훅(Claude Code `settings.json` 등)이 더 강력하지만 **도구마다
제각각이라 이식성이 없다** — MCP 가 툴은 표준화했어도 세션 생명주기 훅은
표준이 없다. git 은 모든 에이전트가 공통으로 쓰는 유일한 표준이라,
도구 중립적으로 강제력을 얻을 수 있는 자리가 여기뿐이다.

## 3. 아키텍처

### 3.1 무게 분포

서버를 일부러 바보로 만들었기 때문에 무게가 클라이언트로 갔다. 의도된 트레이드다.
서버가 똑똑하면 오프라인이 깨지고, 서버가 멍청하면 클라가 무거워지는데
후자가 훨씬 다루기 쉽다.

**서버** — 인증, 저장, 동기화 API. 끝. 임베딩·검색·컴파일 안 한다.

**클라이언트** — 로컬 스토어, 오프라인 큐, 싱크 엔진, 임베딩, 검색,
index.md 컴파일, 스킬 파일 생성, 드리프트 감지, LLM 리베이스, git hook,
backfill, MCP 서버, 칸반 조작.

### 3.2 클라이언트 구조 — 코어 + 얇은 표면

CLI 하나로 만들면 MCP 붙일 때 절반을 다시 짜게 된다. 반드시 분리한다.

```
core (라이브러리)
  store    — 로컬 SQLite
  sync     — 서버 push/pull, 오프라인 큐
  wiki     — 주입, 임베딩, 검색, 컴파일
  skills   — 구현체 생성, 드리프트 감지, 상속/리베이스
  kanban   — 카드 조작
        ↑ 아래 표면들은 core를 부르기만 한다
표면
  knest CLI     — 사람도 에이전트도 치는 것 (정본)
  knest mcp     — MCP로 붙는 것 (같은 프로세스, 서브커맨드)
  git hook      — 큐에 넣고 즉시 종료
```

**에이전트별 훅을 N개 지원하지 않는다.** Claude Code · Cursor · Windsurf ·
Copilot 마다 세션 생명주기 훅이 제각각이라 이식성이 없다(2장 post-commit
절 참고). 그 파편화를 피하는 답이 표면을 소수로 묶는 것이다.

> **2026-08-16 갱신**: 원래 이 자리는 "MCP 하나로 간다"였다. 실제로는
> **CLI가 정본이 됐고 MCP는 병행 표면으로 남았다.** 뒤집힌 이유는 두 가지다.
> (1) 에이전트가 셸을 이미 쓰므로 CLI는 등록 절차 없이 즉시 쓰이는데, MCP는
> 도구마다 서버 등록을 사람이 해줘야 한다 — 무인 루프(0장)에서 이 한 단계가
> 비싸다. (2) 사람과 에이전트가 **같은 명령**을 쓰면 문서·스킬·훅 안내가
> 하나로 끝난다. MCP를 버리진 않았다(`packages/cli/src/mcp.ts`, `knest mcp`) —
> 툴 목록에 자동으로 뜨는 이점이 있어서, 등록해두는 환경에선 그대로 쓴다.
> 대신 **정본은 CLI고, 두 표면 모두 같은 core를 부르므로 기능 차이는 없다.**

## 4. 기술 결정

### 언어 — 전부 TypeScript
서버가 Next.js고 MCP SDK가 TS 네이티브다. 무엇보다 싱크 프로토콜은
서버/클라가 타입을 공유하면 버그가 크게 줄어드는 종류의 코드다.
Python이 임베딩 생태계는 낫지만 언어 두 개를 유지할 값어치는 없다.

### 스택 — Next.js + Prisma + SQLite
로컬 스토어도 SQLite(`better-sqlite3`). 서버와 스키마 모양을 맞추면
싱크가 "행 단위 대조"로 단순해진다.

### 마크다운은 진실이 아니라 export
사람이 읽고 Obsidian으로 열려고 뽑는 뷰다.
**마크다운을 싱크 단위로 삼으면 seed 문서에 기록된 그 지옥이 재현된다.**

### 임베딩 — 로컬 모델, 교체 가능
오프라인 우선이므로 API 임베딩은 주입을 막는다. 코퍼스도 500개 수준이라
작은 로컬 모델로 충분하다. **벡터마다 생성에 쓴 모델·차원을 함께 저장**해서
나중에 모델을 바꿔도 비교가 가능하게 한다.

### 검색 — 키워드 + 벡터 하이브리드
어느 하나보다 낫다. 그리고 **검색 전략을 갈아끼울 수 있는 구조 자체가
평가 시스템의 전제**다. "이번 버전이 나아졌나"를 재려면 전략을 바꿔가며
같은 질문셋을 돌릴 수 있어야 한다.

### 동기화 — LWW로 충분한 이유, 그리고 지금 안 다루는 확장성

> **2026-08-10 갱신**: 원래 제목이 "단일 유저라 쉬운 케이스"였다 —
> 레포 멤버십을 만들면서 전제가 깨졌다. 메커니즘 자체(LWW)는 안 바뀌었고
> 여전히 맞는 선택이지만, "왜 맞는지"의 근거가 "혼자 써서"에서
> "필드 단위 병합이 필요 없어서"로 바뀌었다. 아래는 그 구분과, 지금
> 규모에서 안 다루기로 한 것들을 명시한다.

- 레코드 id는 **클라이언트가 생성**(cuid). 오프라인에서 서버 왕복이 필요 없다.
- 서버는 전역 단조증가 `seq`만 찍는다(레포·유저 무관하게 카운터 하나).
- pull = "내가 멤버인 레포들에서 내 커서보다 큰 seq 다 줘", push = dirty 행 전송.
- 충돌은 **최후 승자 승리 + 진 쪽을 사본으로 보존**(로컬 `conflicts` 테이블).
- **CRDT는 여전히 안 만든다.** 여러 사람이 같은 카드/wiki 엔트리를 동시에
  고치는 게 이제 실제로 가능하지만, 이 시스템은 **행 전체를 한 버전이
  이기는 걸로 취급**하지 **필드 단위로 자동 병합**하지 않는다. 후자가
  CRDT가 필요한 지점인데, 카드 제목 하나를 두 사람이 같은 순간에 고치는
  일은 드물고, 지면 사본으로 남아 사람이 눈으로 보고 되살릴 수 있다.
  "혼자 써서 안 만든다"가 아니라 "행 단위 승자결정으로 충분해서 안
  만든다"로 근거가 바뀐 것뿐, 결론은 같다.

**지금 규모에서 의도적으로 안 다루는 것들** (필요해지면 아래만 갈아끼우면 된다):
- **전역 seq 카운터가 모든 쓰기를 직렬화한다** — 레포·유저 무관하게 카운터
  하나. 인스턴스 하나·팀 규모 트래픽에선 문제없지만, 정말 많은 팀이 한
  서버를 쓰게 되면 쓰기 처리량의 병목이 된다. 그때는 레포별로 시퀀스
  공간을 나누는 식으로 바꿔야 한다.
- **멤버십 조회가 pull/push 마다 한 번씩 붙는다**(`RepoMember` 조회 후
  `IN (...)`). 인덱스는 있지만, 한 유저가 레포 수백~수천 개의 멤버가
  되는 상황은 안 다뤄봤다 — 지금 유즈케이스(개인 여러 프로젝트 + 소규모
  팀)에서는 안 생기는 규모다.
- **레이트 리밋은 인스턴스 메모리 기반**(`deploy.md`에 이미 명시) — 서버를
  여러 대로 늘리면 공유 저장소(Redis 등)가 필요하다.

### 칸반 순서 — 문자열 분수 랭크
`order Int`는 **틀렸다.** 오프라인에서 두 머신이 카드를 옮기면 정수 순서는
반드시 충돌한다. lexo-rank류 문자열 랭크를 쓴다.

### 파생 스킬 저장 — 전문 + 부모 버전 포인터
patch를 저장하지 않는다. 전문을 들고 있으면 바로 쓸 수 있고,
diff는 필요할 때 `부모@그버전 vs 내것`으로 계산하면 된다.
patch 저장은 재구성이 깨지기 쉽다.

**리베이스 흐름**: 부모 v1→v2 감지 → `diff(부모v1, 내것)`과
`diff(부모v1, 부모v2)`를 LLM에 전달 → 병합본 수령 → 사람이 승인 →
파생 v2 생성(`parentVersion=2`). 이전 파생본은 남긴다.

### 스킬 편집 UX — 별도 명령 없음
`.claude/skills/` 안의 파일을 평소처럼 고친다. `knest sync`가 드리프트를
감지하면 "원본과 달라졌는데 파생 스킬로 만들까?"라고 묻는다.
새 워크플로를 배울 필요가 없고, 실수로 날릴 일도 없다.

### 검색 로그는 첫날부터
매 검색마다 `(질문, 반환 결과, 사용된 스킬 버전, 에이전트가 실제로 쓴 결과)`를
기록한다. **나중에 소급이 불가능한 유일한 것**이다. 이 로그에 사후 라벨링만
하면 평가용 정답셋이 공짜로 생긴다.

## 5. 평가 지표 — 나중에, 로깅은 지금

표준 지표는 대략 이렇다:
- 검색이 정답 문서를 상위 k개에 넣었는가 — **recall@k**
- 몇 번째에 넣었는가 — **MRR / nDCG**
- 답변 품질 — 보통 **LLM-as-judge**

셋 다 **"이 질문엔 이 문서가 나와야 한다"는 정답셋이 있어야** 잴 수 있다.
지금 만들 필요 없다. **로깅만 처음부터 하면 정답셋은 나중에 싸게 만들어진다.**

## 6. 만드는 순서

가장 안 해본 것(싱크, 검색 품질)을 먼저 깨고, 아는 것(CRUD, UI)을 뒤로 민다.

1. ✅ **서버 + 싱크 + 칸반** — 칸반을 싱크 프로토콜의 실험동물로 쓴다.
   제일 단순한 엔티티라 프로토콜 버그가 그대로 드러나고, 끝나면 눈에 보이는
   물건이 하나 나온다.
2. ✅ **wiki** — 명시적 주입, 로컬 인덱스, 하이브리드 검색, index.md 컴파일.
   **검색 로그는 여기서부터 무조건.**
3. ✅ **MCP/CLI + git hook + backfill** — 에이전트가 실제로 쓰기 시작하는
   지점. 3층 주입 완성.
4. ◐ **스킬** — 싱크, 구현체 생성, 드리프트→파생, LLM 리베이스.
   **부트스트랩 스킬 생성만 됐다**(1.2 참고). 상속·드리프트 감지·리베이스는
   전부 미착수.
5. ☐ **대시보드 + 카드↔wiki 연결** — "카드 작업 중 나온 지식이 그 카드에 붙는다"가
   통합의 실체이자 한눈에 보기의 알맹이.
6. ☐ **평가 하네스** — 2단계부터 쌓인 로그에 라벨을 붙여 정답셋을 만들고
   스킬 버전 간 비교.

> **1~3이 실제 제품이고 4~6은 확장이다.** 3단계까지 가면 혼자 쓰기엔 충분히
> 돌아간다. 거기서 실제로 써본 뒤 4~6의 우선순위를 다시 정한다.
> 지금 6단계까지 확정 설계하면 4~6은 거의 확실히 틀리게 그려진다.

### 재정렬 — 0장이 다음 순서를 바꾼다 (2026-08-16)

위 1~6은 **개발 루프 하나만 있다고 보고 그린 순서**다. 0장이 들어오면서
"다음에 뭘 하냐"의 답이 바뀌었다. 4~6보다 앞서는 게 생겼다:

- ✅ **4.5 기각 경로 (2026-08-16 구현)** — 0장의 순환은 기각이 상류로 되돌아가야
  닫힌다. `Card`에 `rejectedBy`(qa|dev) / `rejectedReason` / `rejectedAt`을 얹고,
  `knest reject`(CLI) · `kanban_reject_card`(MCP) · 웹 모달에 붙였다. 사유는
  **필수**다 — 비면 거부한다. 사유 없이 되돌리는 건 그냥 이동이고, 받는 쪽이
  같은 실수를 반복한다.

  세 가지를 의도적으로 안 했다: **(1) 기각 이력을 안 남긴다.** 최신 한 건만
  들고 있는다 — 하류가 행동하는 데 필요한 건 "지금 무엇이 문제인가"고, 몇 번
  튕겼는지는 `regressCount`가 이미 센다. 이력이 필요해지면 append-only 엔티티로
  승격하면 되고, 그때 싱크 배관이 하나 늘어난다. **(2) 루프별 컬럼을 안 만들었다.**
  보드가 하나뿐이라 QA 기각이든 개발 기각이든 목적지가 같고, 누가 집어야 하는지는
  `rejectedBy`가 가른다. 루프별로 나뉘면 `toColumnId`만 주면 된다. **(3) 완료에
  다시 도달하면 기각을 지운다** — 안 지우면 이미 고쳐진 사유를 다음 루프가 읽고
  또 손댄다.
- ✅ **4.6 회귀 계기판 (2026-08-16 구현)** — `regressCount`를 기록만 하고 읽는
  쪽이 없었다. `regressionReport()`를 `@kybird/shared`에 두고(core에 두면
  `better-sqlite3` 때문에 웹이 못 쓴다) CLI 보드 하단과 웹 배너가 **같은 임계치**로
  같은 판단을 하게 했다. 임계치는 3회 — 1~2회는 흔한 재작업이고, 3회부터는 카드
  정의나 접근 자체를 의심할 자리다.
- **4.7 QA 루프 → 기획 루프** — 위 둘이 끝났으니 이제 얹힌다. **여기서 설계
  결정이 하나 필요하다**: 루프를 knest 안에서 LLM API 로 돌릴 것인가, 아니면
  지금 `backfill`처럼 **에이전트 세션이 knest 를 호출하는** 형태로 둘 것인가.
  이 코드베이스엔 LLM 클라이언트가 없다(임베딩만 로컬 transformers.js). 후자면
  새 의존성이 없고 0장의 "Z.AI를 주 워커로"와도 맞는다. 전자면 API 키·오프라인
  정책이 전부 새 문제로 들어온다. QA를 먼저 하는 이유는
  입력(완료 카드)이 이미 실제로 쌓이고 있어서 당장 검증 가능해서다. 기획
  루프는 입력이 사람 의도라 더 모호하므로 뒤로.
- **4.8 오프피크 무인 기동** — 위가 돌기 시작한 뒤. 루프가 사람 없이 몇 시간
  버티는 게 확인되기 전에 스케줄링부터 만드는 건 순서가 틀렸다.

5(대시보드)·6(평가 하네스)는 그대로 뒤에 둔다. 다만 대시보드의 값어치는
0장 기준으로 올라간다 — 무인 루프가 밤새 돈 결과를 아침에 사람이 몰아서
보는 자리가 곧 대시보드이기 때문이다(0장 "승인은 루프 밖으로").

1. ~~**CLI 이름**~~ — **해소(2026-08-16 확인).** `knest`로 확정됐다.
   `packages/cli`의 bin, AGENTS.md, 부트스트랩 스킬, README가 모두 이

2. **지식의 프로젝트 독립성** — 주입 시점에 아예 "프로젝트 종속 / 프로젝트 독립"을
   구분해 저장하는 안이 나왔으나 미결. cross-project 검색의 품질과 직결된다.
3. **세션 저장** — 서버에 저장하는 건 스코프 밖으로 판단. 다만 로컬에 이미 있는
   에이전트 트랜스크립트를 **사후에 긁어오는** 형태는 열려 있다.
   에이전트별로 위치·포맷이 다르지만 **읽기 전용이라 하나씩 늘리면 되고,
   미지원 도구는 backfill로 떨어지므로 깨지지 않는다.**
   **2026-08-09 메모**: 이게 필요한 이유는 git 커밋이 "최종 결과"만 남기기
   때문이다 — 시행착오·버린 시도·커밋 없이 끝난 세션(조사만 하고 끝, 설정
   삽질)은 커밋 기반 backfill에 아예 안 잡힌다. 다만 이건 커밋 기반
   backfill과 별개로 **진짜 파편화 문제**다 — 세션 트랜스크립트는 git에
   안 들어가는 로컬 파일이라 각자 자기 머신에만 있다. (레포 공유 기능을
   만들면서 다른 파편화 문제 하나는 이미 고쳤다: `ingest_queue`가 로컬
   전용이라 팀원끼리 "이 커밋 이미 처리했나"를 몰랐던 것 — `WikiEntry.
   sourceRef`로 이미 처리된 커밋인지 확인하는 걸로 해결, `Store.
   hasSourceRef()`. 이건 커밋 자체가 git으로 이미 공유되니까 가능했던
   것이고, 세션 트랜스크립트는 애초에 공유되는 원본이 없어서 같은 수로는
   못 푼다.)
   **2026-08-10 갱신**: 세션 트랜스크립트 파싱 대신, 옛 TTSTextViewer의
   `doc/raw/Case N`이 실제로 하던 역할 — "저비용 원본 캡처 → 나중에
   압축" — 을 **구현했다.** `wiki_raw`(MCP)/`knest wiki raw`(CLI) →
   `captureRaw()`(`packages/core/src/git.ts`)가 `doc/raw/<작성자
   이메일>/<날짜>.md`에 append 하고 즉시 커밋한다. **사용자별로 파일을
   쪼갠 게 핵심** — 옛 시스템이 겪은 "여러 주체가 같은 파일에 써서 충돌"
   (index.md 10%, raw 파일 Case 번호 중복)을 구조적으로 재현하지 않는다.
   커밋되면 그 자리에서 바로 `enqueueIngest`도 해서(훅 설치 여부와
   무관하게 확실히 큐에 들어감, `(repoId, ref)` 유니크라 훅이 나중에
   또 넣어도 안전) 기존 backfill 파이프라인이 그대로 소화한다 — 새
   동기화 배관 없음, `doc/brief.md` 6장 3층 구조 그대로. 이걸로 이
   항목은 "세션 트랜스크립트 자체를 긁는" 원안보다 훨씬 싸게, 사실상
   같은 가치를 이미 달성했다고 본다 — 완전히 닫힌 건 아니지만(정말
   세션 통째 스크레이핑이 필요해지면 그건 여전히 별도 작업) 지금은 이걸로
   충분해 보인다.
4. **기존 자산 마이그레이션** — TTSTextViewer의 466개 항목. 천천히 한다.
   가져오면 평가용 실데이터가 처음부터 생긴다는 이점은 있다.
