# kybird-nest — 시작 논의 원본 (2026-08-08)

> 이 문서는 SSOT가 아니다. TTSTextViewer 저장소 세션에서 나눈 설계 논의를
> 유실 없이 옮겨 적은 **원재료**다. 여기서 결정/보류/미결을 추려 별도 SSOT
> 문서(예: `doc/brief.md` 또는 `doc/spec.md`)를 만들어간다.

## 출발점

TTSTextViewer(`doc/wiki/` + `.agents/skills/wiki-*`) 프로젝트에서 자체
구축한 raw-log → wiki 컴파일 지식 시스템을 검토하다가, 이걸 프로젝트 밖으로
승격하자는 논의로 발전했다. 논의 도중 목적 자체가 "wiki 승격"에서
"코딩에이전트 스킬킷 전체(위키 포함)"로 확장됐다.

## 문제 인식 (기존 TTSTextViewer 시스템에서 관찰된 것)

1. **위키 컴파일 산출물(`doc/wiki/index.md`)을 git에 커밋**하고 있었다.
   - 매 컴파일마다 `Last updated` 날짜, `Total concepts/patterns/...` 통계,
     알파벳 정렬된 466개 항목 표가 전부 다시 쓰임.
   - 전체 1145 커밋 중 115개(10%)가 이 파일 하나. 두 장소에서 컴파일하면
     사실상 100% 충돌.
2. **raw 로그가 "하루 1파일"** (`doc/raw/YYYY-MM-DD.md`), 그 안의 `## Case N`
   번호를 **각 로컬이 독자적으로 계산**해서 부여.
   - 실제로 `2026-04-21`, `2026-05-12`, `2026-08-02.md` 등 7개 파일에서
     Case 번호 중복 확인됨 — 서로 다른 브랜치/시점에 각자 "마지막이 N-1이네"
     라고 판단해 같은 N을 두 번 씀.
   - 커밋 메시지의 `doc/raw/2026-08-05.md Case 10` 같은 링크가 모호해짐.
3. **스킬이 두 스코프에 흩어져 있고 그중 하나만 버전관리됨**:
   - 프로젝트 스코프 `.agents/skills/` ↔ `.claude/skills/`는 정본/복사본
     미러 + pre-commit drift 가드로 **완전히 동기화됨** (드리프트 0).
   - 머신 스코프 `~/.claude/skills/`, `~/.claude/plugins/`는 **버전관리 밖**.
     예: superpower 같은 스킬을 집 데스크톱에 설치하면 노트북엔 없음.
     이건 우연이 아니라 전역 설치의 구조적 필연.
4. (부가 발견, 우선순위 낮음) `wiki-compile`이 생성하는 frontmatter가
   닫는 `---`가 없어 Obsidian이 인식 못 할 가능성. `wiki-search`의 grep
   폴백이 Windows 전용 `findstr`이라 크로스플랫폼 배포 시 깨짐.

## 프로젝트 성격 재정의

처음엔 "wiki 시스템 하나를 떼서 npm 배포"로 시작했으나, 대화 중
**"위키뿐 아니라 스킬 전체를 필요할 때 가져다 쓰는 킷"**으로 스코프가 커짐.
근거: 현재 `.agents/skills/` 16개 중 TTSTextViewer 전용은 0개
(wiki-* 4개, flutter-* 7개, ask-browser-ai/ssh-agent-delegation 등 나머지도
전부 범용) — 즉 이미 이식 가능한 상태로 만들어져 있었고, 프로젝트가 그걸
가둬두고 있었을 뿐.

## 핵심 설계 결정 (확정)

### 1. 설치 단위 = 레포지토리
스킬을 개별 단위나 패키지 단위로 add/remove 하는 게 아니라,
**레포지토리 자체가 설치 단위**다. (개별 스킬 add/remove 모델은 한때
논의됐다가 이 결정으로 대체됨 — 아래 "재검토 필요" 참고.)

### 2. 서버가 스킬 구성 + 실행 결과물을 함께 관리
처음엔 "스킬 구성(A, 거의 안 바뀜)"과 "스킬 실행 결과물(B, wiki 콘텐츠,
자주 바뀜)"을 분리해서 서버는 A만, B는 기존 git 방식 유지하는 안을
제안했었음. 사용자가 최종적으로 **A+B 둘 다 서버가 담당**하는 걸로 확정.

이게 가능해진 이유: **혼자 쓰는 환경이라 진짜 동시편집 충돌이 희귀**하고,
지금까지 겪은 "충돌"은 사실 여러 로컬이 각자 다음 번호(Case N)를
독자적으로 계산해서 생긴 문제였음. → **서버가 번호를 원자적으로
발급하는 단일 카운터가 되면 이 충돌 자체가 구조적으로 불가능해짐.**
CRDT나 병합 로직이 필요한 문제가 아니라 auto-increment 문제로 축소됨.

확정된 흐름:
```
로컬 스킬 실행 (wiki-log 등)
  → 내용(content)은 AI가 작성
  → 번호/저장은 서버가 담당: POST /repos/{repo}/raw/entries
  → 서버가 원자적으로 ID 발급, authoritative 저장
  → 로컬은 응답을 받아 로컬 캐시(markdown)로 미러 (오프라인 열람·가독성용)

wiki-compile / wiki-search / wiki-lint
  → 서버가 가진 전체 raw entry 대상으로 동작 (or 로컬 캐시 fallback)
  → 컴파일된 wiki도 서버가 authoritative, 로컬은 미러

오프라인 시나리오
  → 서버 접속 불가하면 로컬에 큐잉
  → 재접속 시 flush, 그 시점에 번호 확정 (오프라인 중 여러 머신이 각자
    써놔도 flush 순서대로 병합되므로 충돌 없음)
```

이 모델에서 **로컬 markdown 파일은 진실 원천이 아니라 서버의 캐시/미러**가
된다. git 커밋은 사람이 diff로 보고 싶을 때 쓰는 선택사항이지, 동기화
메커니즘이 아니게 됨.

### 3. 레포 식별
- 기본: **git remote URL**.
- remote가 없는 로컬 전용 레포: **머신 고유 ID + 디렉토리 경로** 조합으로
  임시 식별.
- 나중에 remote가 생기면 그 주소로 레포 ID를 갱신(마이그레이션).
- (이전에 논의됐던 대안: 레포 내 `.kit/repo-id` 파일을 커밋해 명시적으로
  식별하는 방식 — remote URL 방식으로 결정되며 보류됨.)

### 4. 이름
- 패키지/브랜드명: **`kybird-nest`** (확정).
- 후보로 나왔던 것: `stratawiki`(지층 은유, wiki 전용으로 스코프가 좁을 때
  후보였음 — 스코프 확장으로 폐기), `kybird-hive`/`roost`/`flock`/`loom`
  등(새 테마 대안, `nest`가 "스킬+콘텐츠를 모아 쌓아두는 곳"이라는 의미와
  가장 잘 맞아 최종 선택).
- CLI 이름 후보: `nest` (예: `nest add`, `nest sync`, `nest push`) —
  **미확정**, 이 문서 기준으로는 논의만 되고 확정 안 됨.
- 기존 npm `llm-wiki`(월다운로드 174, placeholder로 시작한 개인 프로젝트,
  같은 컨셉의 직접 경쟁자)로부터 이름을 물려받는 안은 **기각**. `@kybird/`
  스코프 자체는 기술적으로 가능하나, 이름 자체를 고유하게 가져가는 쪽으로
  최종 결정.

## 재검토가 필요한 지점 (이 문서 작성 시점 기준 미해결/모순 가능성)

1. **"설치 단위 = 레포지토리" 결정과, 그 이전에 나온 "패키지(그룹) 안에
   스킬 여러 개, 개별 스킬 add/remove" 설계가 어떻게 공존하는지 불명확.**
   레포 단위 설치가 "이 레포에 킷 전체를 붙인다"는 뜻인지, 아니면
   "서버 쪽에서 레포별로 어떤 스킬 조합을 쓰는지 추적하는 단위가
   레포"라는 뜻인지 구분 필요. 후자라면 개별 스킬 add/remove와 모순되지
   않음 — SSOT 작성 시 명확히 할 것.
2. **레포 내 스킬 파일의 실제 형태**: 지금처럼 `.agents/skills/`에 실물
   파일로 존재하고 서버는 그 변경 이력만 추적하는지, 아니면 서버가
   authoritative고 로컬엔 sync 결과물만 내려오는지 — 스킬 구성(A)에
   대해서는 아직 명시적으로 정해진 바 없음 (raw 콘텐츠(B)는 위에서
   확정됨).
3. **서버 스택/호스팅**: 사용자가 "내가 직접 호스팅하는 서버"라고 언급.
   기존 VPS 존재 여부, 스택(런타임/DB) 미논의.
4. **CLI 상세 커맨드셋**: `kit add/remove/list/sync` 초안이 여러 번
   나왔으나 "레포 단위 설치"로 최종 방향이 바뀌면서 재설계 필요.
5. **frontmatter 버그, findstr 크로스플랫폼 버그**: 기존 TTSTextViewer
   구현의 결함이므로 kybird-nest로 로직을 옮길 때 그대로 이식하지 않도록
   주의.
